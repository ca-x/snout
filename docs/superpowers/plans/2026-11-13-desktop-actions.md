# Desktop action hierarchy implementation plan

> 执行方式：主 agent 按任务实施；独立 agent 先评审本方案，所有阻塞意见达成共识后才修改产品代码。开发完成后再验证和发布。

**Goal:** 将更新、配置保存、外观应用放在对应任务中，消除重复入口，清楚表达操作范围与结果。
**Architecture:** 延用 NSH 0.4.0、共享 Rust 服务、单后台工作线程和现有主题系统。统一 app-owned 按钮层级和底部配置操作条；新增有限的“保存配置后安装”后台命令，复用现有服务。
**Tech Stack:** Rust、NSH 0.4.0 原生视图、nsh-testing Headless；CLI/TUI 共用核心。
**Spec:** 本文第 1–5 节；现有基础为 `docs/desktop-design.md`。
**评审基线:** `fb2b2c52ee0f5afa98a6fee042668342df36ea15`。当前只写方案，未改产品代码。

## 1. 用户与范围

面向日常维护 Rime 的桌面用户；常用任务是更新、切换方案、调整外观。沿用系统字体、蓝色语义 token、现有 8/12/16/24 间距和 6–12 圆角。说明保持简短，中英两种语言均完整。

本次修改桌面按钮归属、保存/安装流程、外观应用反馈、活动页信息分组。TUI 主菜单已集中一次更新入口，各项快捷键 1–8/Q 各有不同作用，保留其现有结构；只在共享行为确实发生变化时补回归验证。

最小方案是只把全局更新按钮挪到概览并删掉重复保存按钮，但它保留“选方案→保存→再安装”的断裂流程。本方案增加一个有明确阶段的组合操作，减少这个常见任务的往返。

不增加依赖、配置项、外部服务、CLI 参数或新的导航目的地。沿用现有平台支持判断、凭据脱敏、数据保护、取消能力与主题市场多变体行为。

## 2. 按钮归属与层级

| 位置 | Before | After | 原因 |
| --- | --- | --- | --- |
| 全局页头 | 所有页面显示“更新全部” | 只保留标题和简短说明 | 页头不承载与当前任务无关的更新操作 |
| 概览当前方案 | 切换方案、调整外观两处侧栏副本 | 主要“更新全部…”；次要“检查更新” | 让主要维护任务一眼可见；侧栏负责导航 |
| 概览组件 | 状态卡与下方三颗分离的更新按钮 | 每个组件一行，信息与“更新…”同行 | 控件紧靠所影响对象；保留有用的独立更新 |
| 概览引擎 | 检查/设置 Rime + 刷新诊断并列 | “配置 Rime…”为次要操作；刷新进入诊断展开区 | 设置引擎与读取诊断不混在一起 |
| 方案页 | 页面保存、底部保存条、安装共三处 | 页面底部只有一个上下文操作区 | 消除同一保存的多个副本 |
| 设置页 | 页内保存/还原 + 底部保存/还原 | 只使用共用底部操作条，未改动时不显示 | 保存全部配置的范围一致 |
| 外观候选数 | 应用 + 单独恢复默认 | 选择器内加入“方案默认”，只有一个“应用” | 恢复默认与选择数字走同一流程 |
| 外观皮肤 | 自定义的裸按钮样式 | 使用统一按钮组件，作用域写入所在区域 | 统一可用性、焦点、按下、忙碌反馈 |
| 活动页 | 日志、原始 JSON、Shell 补全同级 | 日志/结果优先；JSON 作为详情；Shell 补全移到设置的工具区 | 减少非当前任务的干扰；保留所有导出能力 |

按钮层级新增 `Primary / Secondary / Quiet / Destructive` 明确枚举，替代页面对 bool 和裸 button 的零散样式。重点是常规操作层级；选项卡、选择卡片、开关继续使用各自语义控件。

- Primary：当前任务唯一主操作。概览为更新全部；方案为安装；设置在存在改动时为保存。
- Secondary：检查更新、配置 Rime、各外观区域的应用。
- Quiet：单独组件更新、查看仓库、查看已下载主题、诊断刷新、导出与还原。
- Destructive：仅确认界面中明确丢弃数据或重置的操作。
- `38pt` 桌面默认高度、明确焦点环、可读禁用态，保留现有 token。
- 保留约 120ms 的颜色反馈及即时按下态；不增加路由动画、弹跳或点击等待。减少动态效果时仍可识别状态。

### 布局示意

概览

└──────────────────────────────────────────────────┘

  词库       本地版本 / 记录时间             更新…
  模型       本地版本 / 记录时间             更新…

▸ 诊断与文件位置                  （展开后有刷新）

输入方案                         设置

  （无页内保存副本）               （无页内保存副本）

概览方案身份取已保存 `Snapshot.config`，文案使用“所选方案”，不拿尚未保存的 UI 草稿冒充已安装方案。安装完成仍以安装记录为准；组件区域标记本地记录，不承诺偏好保存即代表新方案已经部署。

## 3. 保存、安装与确认

### 3.1 单一配置操作条

配置草稿仍可跨页保留，操作条说明“有未保存的配置修改”，还原针对全部配置草稿。dirty 必须表示草稿与已保存配置实际不同，改回原值后操作条消失。

| 页面/状态 | 操作区 |
| --- | --- |
| 方案页，无配置修改 | 主操作“安装所选方案…”；作用对象显示选中方案名称 |
| 方案页，有配置修改 | 主操作“保存并安装…”；次要“仅保存”；低强调“还原” |
| 其他页面，有配置修改 | 主操作“保存修改”；低强调“还原” |
| 其他页面，无配置修改 | 不显示配置操作条 |

方案页静态页尾不再重复安装按钮，以上内容在同一个固定底部区域呈现。Mod+S 始终只保存草稿，不触发安装。切换页面不会写配置或自动安装。概览更新遇到未保存配置时禁用，并由操作条提示先保存或还原。

焦点规则：操作条消失或控件替换前，只有焦点仍位于该区时才转移到稳定目标；方案页为保留的安装按钮，其他页为当前页侧栏导航按钮。组合安装主动转入活动页时聚焦活动状态区。异步等待期间用户若已主动把焦点移走，完成时不抢回。确认取消/Escape 返回原触发控件。实现使用 NSH ElementRef 和焦点事件，不依赖 DOM 或假定未挂载控件可被聚焦。

### 3.2 组合安装的精确边界

新增 `Command::InstallScheme { config: Box<Config>, preserve: bool }`。用户只确认一次，后台同一请求串行：

1. 校验完整配置；保存失败则不启动安装。
2. 调用 `application::save_settings` 保存配置（含已有模型补丁同步语义）。
3. 调用共享 `run_update(UpdateAction::All, ...)` 安装所选方案及其支持的组件。

当前“安装所选方案”本就运行 All，继续保持，界面确认摘要必须说明会同步方案及其支持的词库/模型。确认中展示方案名、目标目录、保留/丢弃数据政策及 hooks；存在其他页的草稿时说明“同时保存其他设置”，不能悄悄丢弃或只保存部分。

保存结果与安装结果分别传递：每个组合请求的完成信息包含 `settings_saved: bool`，该值在请求开始时为 false，只有 `save_settings` 返回 Ok 后为 true；不从最终 Status 推断。UI 只根据该值更新已保存基线和 dirty，安装仍使用独立的 Success / PartialFailure / Cancelled / Error。其他请求不继承这个标记。

活动页与导出 JSON 使用现有 Report.results 结构加入一条 `component: "settings"` 的配置保存结果，success 表示是否保存完成，message 说明未执行/失败/已保存；安装组件结果正常保留。不新增 JSON 字段、不更改 schema_version。保存成功但安装失败时整个 report.ok 仍为 false。安装状态只根据安装组件计算，不能因为 settings 条目成功而把全部安装失败归为部分成功。请求预取消、preview 拒绝、保存失败均不进入安装、保留原配置草稿；保存成功后的取消清理已保存 dirty，保留新配置。

`preserve` 仅覆盖本次安装使用的配置副本，沿用现有 Update 命令逻辑，不修改已经保存的 user_data_policy 偏好。

此操作不是跨文件事务：保存成功但安装失败/取消时保留已保存配置，明确显示“设置已保存，安装未完成”，允许重试；不可显示完整成功或继续保留已保存的 dirty。保存阶段出错则保留草稿。若部分组件成功，展示部分失败报告，主操作可重试。实际安装状态仍以已有安装记录与检测结果为准，保存偏好不等于已安装。重启沿用 Manager::new 的检测覆盖规则，不额外承诺失败后的偏好跨重启保留；测试覆盖已安装 A 仅保存 B、保存 B 后安装失败两种身份展示。

请求的 `Config` 和 preserve 值在确认时捕获，执行时不读另一份可变 UI 草稿。忙碌时不能重入，取消继续使用 CancelSignal；阶段间检查取消。隔离 preview 必须在任何保存/安装写入之前拒绝组合命令，不可意外绕过 live guard。

### 3.3 中途取消与已完成结果

取消是终止原因，不是回滚。共享 `update_all` 在抛出取消错误时必须携带此前完成的组件结果，桌面/CLI/TUI 能取回这些结果；原有 `UpdateCancelled` 识别仍成立。界面明确“已完成的更改不会撤销”，不宣称完整安装成功。

最小实现允许在共享更新函数外层保留结果集合，为取消错误附加携带 completed results 的 typed context；客户端使用一个共享提取函数，保持现有 `Result<Vec<UpdateResult>>` 公共返回类型及 JSON 外形。每个后续阶段开始前检查取消；任一阶段取消后不继续部署、同步或 hooks。原错误文本及取消原因不丢失。不要为了结果保留新增事务框架、服务或重试。

测试必须以确定性的阶段完成/取消输入覆盖真实的结果收集与停止边界，验证至少一个组件已完成后取消：最终取消、报告保留已完成组件、保存结果独立存在、后续阶段未开始；不能仅手工构造最终 Report 或仅测预取消。允许一个最小的内部测试注入点（假的阶段执行函数）覆盖共享调度路径，不要求真实网络、真实 Rime 或真实 hooks。

### 3.4 精确确认

普通网络/界面偏好保存直接执行并显示保存结果；`save_settings` 的真实同步条件是 `model_patch_enabled` 改变，或 schema 改变且新配置启用模型补丁，涉及这些更改时保留一次准确的确认。

安装更新、hooks 执行、用户数据丢弃和重置仍显式确认。确认标题与按钮使用具体动词，如“更新全部组件？”、“保留数据并更新”，不用“继续前请确认 / 确认”。Cancel/Escape 返回原操作位置、保留草稿。

不改变现有 data policy 的含义；保留数据为正常路线，丢弃数据保持明确的破坏性选项。取消不得提交命令。模型补丁开关不支持的方案继续隐藏。

## 4. 外观与反馈

Fcitx5 的“本地主题 / 主题市场”、按仓库查看多主题、浅/暗模式选择、原始主题圆角支持判断继续保留。

- 全局配置存在未保存修改时，禁用各区域 Apply，原处提示“先保存或还原配置”；保留所有外观选择。处理配置后恢复可应用状态。候选数的写入目标始终为已保存方案；方案切换成功后重新加载该方案的候选草稿，不能把 A 的候选草稿自动用于 B。
- 每个独立外观区域有自己的“应用”，改动只影响该区域；不造一个容易跨区域漏保存的全页 Apply。
- 已应用/没有改动时禁用应用按钮。保存全局设置不应用候选数或主题，应用主题不保存其他配置草稿。
- 候选数选择类型使用 `Option<u8>`：None=方案默认，Some(1..=9)=显式覆盖。原生选择器中显示“方案默认”。仅改变选择不写入。点击“应用”一次提交 CandidateSize；不再用单独 ResetCandidate 确认。
- 不知道实际 schema 默认候选数时，预览注明是“布局预览”，不得把示例 5 当成真实默认值；显示“方案默认”，不假报已解析的数字。
- 候选数和皮肤草稿不应被刷新、市场下载或保存网络设置覆盖；仅当权威字段改变时同步，或当前应用成功后清理该区域草稿。
- 应用中显示执行状态，成功显示“已应用”，失败原处显示原因并能重试；失败保留用户选择。不把全局上次主题成功当作另一项应用成功。
- 允许导航查看活动，后台写操作保持单个工作队列。操作进度/结果保留在共用状态区；活动页不再常驻一个无关的更新按钮。
- 主题市场的 Download/Update/View themes/Repository 使用一致按钮层级，仓库链接用低强调样式；不改下载去重/导入规则。

## 5. 验收与发布门槛

### 行为

1. 手动维护更新入口仅在概览（update-all 只在概览）；方案页保留安装任务，市场更新只针对主题仓库；侧栏和 Mod+1…5 可达所有页面。
2. 概览单独组件更新指向正确 UpdateAction；不支持独立词库的方案隐藏该项更新，模型动作依据既有能力判定，不提供无效按钮。
3. 方案/设置无重复 save/revert；回改值不再 dirty；Mod+S 不启动安装。键盘保存、还原、组合安装部分失败后焦点落到稳定位置；用户已主动转移焦点时不被异步结果抢回。
4. 保存并安装：取消确认无写入；保存失败不安装；保存成功后安装失败/取消明确区分结果并清理已保存 dirty；隔离 preview 不允许组合写入。
5. 数据保护、hooks 警示、凭据脱敏、取消、部分失败仍成立。组件完成后取消保留已完成结果并停止后续阶段；配置保存结果独立可辨。补丁写入失败的原始 YAML 回滚测试必须保留，回滚失败不得宣称无副作用。
6. 全局 dirty 时外观 Apply 禁用且就地解释，处理草稿后保留外观选择（切换方案则重载候选目标）。候选默认/显式值只在 Apply 后写入，未改动禁用；失败可重试；其他操作不覆盖各外观区域未应用草稿。
7. 原有多仓库主题混选、失败重试、滚动保持回归通过。
8. 活动 JSON 详情/导出仍可访问；补全导出移到设置后仍使用真实 CLI 定义。
